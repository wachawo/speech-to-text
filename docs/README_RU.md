`speech-to-text` превращает аудио в текст с помощью [openai-whisper](https://github.com/openai/whisper), обёрнутого в небольшой HTTP-сервис, который вы запускаете сами. Вы отправляете аудиофайл и получаете обратно его транскрипцию. Никакого внешнего API, никакой оплаты за минуты, и ваше аудио никогда не покидает вашу машину.

Проект подходит для локального использования, пакетной транскрипции и запуска собственного STT-сервера в сети.

* **Готовый к работе HTTP-сервер.** Flask под управлением uvicorn загружает Whisper при старте и отвечает на запросы с других машин в вашей локальной сети.
* **Безопасность при параллельных запросах.** Сервер держит пул предварительно загруженных экземпляров Whisper, поэтому несколько запросов транскрибируются параллельно без повторной загрузки модели.
* **CPU или GPU, один и тот же код.** Бэкенд выбирается окружением и тем, какой Docker-образ вы собираете. Видеокарта с CUDA ускоряет инференс, но всё работает и на CPU.
* **В комплекте идёт CLI-клиент.** `stt_client.py` отправляет локальные файлы на сервер и выводит результат.
* **Транскрипция в реальном времени.** Передавайте аудио потоком через WebSocket и получайте каждую фразу по мере того, как она произносится, с привязкой к говорящему, если включена диаризация.
* **В комплекте идёт веб-интерфейс.** Загрузите файл в браузере и прочитайте текст или кто что сказал; интерфейс отдаёт собственный nginx-контейнер рядом с сервером.

### Модели

Whisper поставляется в нескольких размерах моделей. Более крупные модели точнее и медленнее, более мелкие быстрые и лёгкие.

| Модель     | Параметры  | VRAM    | Языки           | Подходит для                                  |
| ---------- | ---------- | ------- | --------------- | --------------------------------------------- |
| `tiny`     | 39M        | ~1 GB   | многоязычная    | быстрые черновики на слабом железе            |
| `base`     | 74M        | ~1 GB   | многоязычная    | лёгкий универсальный вариант по умолчанию     |
| `small`    | 244M       | ~2 GB   | многоязычная    | хороший баланс точности и скорости            |
| `medium`   | 769M       | ~5 GB   | многоязычная    | выше точность, если можно выделить память     |
| `turbo`    | 809M       | ~6 GB   | многоязычная    | точность близкая к `large`, намного быстрее   |
| `large`    | 1550M      | ~10 GB  | многоязычная    | лучшее качество, требуется GPU                |

Англоязычные варианты (`tiny.en`, `base.en`, `small.en`, `medium.en`) чуть точнее на английском аудио. По умолчанию используется `turbo`, лучший универсальный выбор для английского на GPU.

#### Несколько моделей

`STT_MODELS` загружает при старте несколько моделей распознавания, у каждой свой пул, и позволяет каждому запросу выбрать одну из них через `model`. Записи перечисляются через запятую в виде `backend:model[@pool]`:

```bash
STT_MODELS=whisper:turbo@2,whisper:small.en@1,parakeet:nvidia/parakeet-tdt-0.6b-v3@1
STT_DEFAULT_MODEL=turbo    # модель для запроса без `model`; пусто означает первую запись
```

Выбор идёт только среди моделей, загруженных при старте: запрос никогда не запускает скачивание или загрузку, а незагруженная модель отклоняется с `400`. Каждая модель из списка занимает память, пока работает сервер, примерно `воркеры x (пул x размер модели)`, просуммированное по списку, плюс диаризатор. `turbo@2,small@1,parakeet@1` на GPU занимает около 12 + 2 + 3 = 17 ГБ на процесс. Под gunicorn каждый sync-воркер обрабатывает один запрос за раз, поэтому ставьте каждой записи `@1` и масштабируйтесь через `GUNICORN_WORKERS`. Запись без `@pool` получает `STT_POOL_SIZE`, а вне Docker это 8, поэтому пишите `@N` явно. Несколько больших моделей грузятся дольше одной, поэтому увеличьте `start_period` у healthcheck в compose-файле, если контейнер помечается unhealthy во время старта.

Когда `STT_MODELS` пуст, `STT_BACKEND`, `WHISPER_MODEL` и `PARAKEET_MODEL` выбирают единственную модель, как раньше, и сервер загружает ровно то же, что и раньше; в ответах только появляются новые поля. Когда он задан, эти переменные больше не определяют, что загружается. В Docker задавайте `STT_MODELS` и `STT_DEFAULT_MODEL` в `.env`, а не в блоке `environment:` compose-файла, который перекрывает `.env`. Запись Parakeet по-прежнему требует образа, собранного с `PARAKEET=true`, а сервер не стартует при неизвестном бэкенде, при одних и тех же весах в двух записях (`turbo` и `large-v3-turbo`) или при `STT_DEFAULT_MODEL`, которого нет в списке. Модель, заданная путём к файлу, отдаётся под именем файла без `.pt`, так что путь никогда не попадает к клиенту. `STT_DEFAULT_MODEL` может назвать такую запись этим именем или путём ровно так, как он записан в `STT_MODELS`, а языки у неё те же, что у чекпойнта, названного в имени файла: `/models/large-v3.pt` знает то же, что `large-v3`. Две записи, которые обслуживались бы под одним именем (`/a/model.pt` и `/b/model.pt`), или запись, которая обслуживалась бы под именем бэкенда (`/models/parakeet.pt`), останавливают сервер при старте.

### Быстрый старт (Docker)

Проще всего запустить сервер через Docker. Файлы моделей кешируются в `./models` на хосте, поэтому они переживают пересборку контейнера.

```bash
git clone https://github.com/wachawo/speech-to-text.git
cd speech-to-text

docker compose up --build                              # GPU (CUDA 13.0)
docker compose -f docker-compose-cpu.yml up --build    # CPU only
```

Для сборки под GPU на хосте нужен `nvidia-container-toolkit`. При первом запуске модель Whisper скачивается в `./models`. Работа на сервере - обновления, откаты, сертификаты, зависимости - описана в [docs/DEPLOY.md](DEPLOY.md).

### Веб-интерфейс

`docker compose up` также запускает `stt_www`, nginx-контейнер, который отдаёт браузерный интерфейс и пропускает `/api/` на сервер, так что интерфейс и API доступны по одному адресу. Он слушает один порт, `STT_WWW_PORT` (по умолчанию `5053`), по https, если не задано `STT_WWW_SCHEME=http`.

Откройте `https://<host>:5053`. У **TRANSCRIBE** три источника. **FILE** загружает аудиофайл. **DEVICE** транскрибирует в реальном времени со звукового входа: микрофона или гарнитуры, источника `Monitor of ...` в Linux, который несёт всё, что играет через динамики или наушники, или, в браузерах на Chromium, `Tab or screen audio` для того, что играет во вкладке браузера, либо во всей системе, где ОС это позволяет. **STREAM** принимает адрес потока или удалённого файла - интернет-радио, HLS, RTMP, RTSP, SRT - и сервер читает его сам. В любом случае результат появляется под формой обычным текстом или, при включённой диаризации, блоком на каждую фразу с говорящим и временем, где у каждого говорящего свой цвет, а фразы, в которых двое говорили одновременно, помечены; фраза в реальном времени появляется примерно через секунду после того, как говорящий делает паузу. Результат можно скопировать или скачать как TXT или JSON, и каждый источник хранит свой последний результат, пока вы смотрите другой экран. У FILE есть также режим **Turns**, то есть `POST /api/diarize` сам по себе: кто и когда говорил, в виде временной шкалы с отдельной дорожкой на каждого говорящего, где отмечены отрезки, когда двое говорят одновременно. Если загружено несколько моделей (`STT_MODELS`), выбор модели рядом с режимом и языком задаёт модель для всех трёх источников - FILE, DEVICE и STREAM; список берётся из `GET /api/models`, а список языков следует за выбранной моделью. Turns ничего не распознаёт и модель не отправляет. **MODELS** показывает то, что сообщает `GET /api/models`. Если задана переменная `STT_TOKENS`, интерфейс один раз запрашивает токен и хранит его в браузере.

Браузеры отдают аудиоустройства только защищённой странице, поэтому по сети DEVICE нужен https; в режиме http он работает только на `http://localhost`. В режиме https обычный запрос `http://` на этот порт перенаправляется на https, а контейнер при первом запуске создаёт самоподписанный сертификат в `./data/certs`; чтобы заменить его, положите туда настоящие `stt.crt` и `stt.key`. У интерфейса нет этапа сборки и нет CDN: Vue 2 и его библиотеки лежат в репозитории в `www/vendor`, поэтому он работает на машине без выхода в интернет.

### HTTP API

Когда сервер запущен, проверьте его статус и отправьте аудиофайл на транскрипцию.

```bash
curl localhost:5051/api/health

curl -X POST localhost:5051/api/stt \
  -F file=@speech.mp3

curl -X POST 'localhost:5051/api/stt?language=ru' \
  -H 'Content-Type: audio/wav' \
  --data-binary @speech.wav
```

`GET /api/health` возвращает статус пулов. Поля верхнего уровня `pool_size` и `available` описывают модель по умолчанию, ту, которую ждёт запрос без `model`; падение `available` до 0 означает, что все её экземпляры сейчас заняты. `models` сообщает о каждой загруженной модели по её id:

```json
{ "status": "ok", "pool_size": 2, "available": 1, "diarize": false, "default_model": "turbo",
  "models": { "turbo": { "backend": "whisper", "pool_size": 2, "available": 1 },
              "nvidia/parakeet-tdt-0.6b-v3": { "backend": "parakeet", "pool_size": 1, "available": 1 } } }
```

Если задан `STT_TOKENS`, `default_model` и `models` попадают только в ответ на запрос с действительным токеном: как и `GET /api/models`, они раскрывают конфигурацию сервера. Healthcheck без токена по-прежнему получает `status`, `pool_size`, `available` и `diarize`.

`GET /api/health?deep=1` дополнительно прогоняет секунду тишины через каждую загруженную модель, по одной, и сообщает для каждой `ok`, `busy` (за пять секунд не освободился ни один экземпляр) или `failed`: каждую модель распознавания по её id в `deep.models`, худший из их результатов в `deep.transcriber` и `deep.diarizer`, когда диаризация включена. Если хоть одна дала сбой, ответ будет `503`. Это стоит работы GPU, поэтому, пока задана `STT_TOKENS`, такой проверке нужен токен; простая проверка остаётся открытой для проверок состояния контейнеров.

`GET /metrics` отдаёт метрики Prometheus: запросы по маршрутам и статусам, их длительность, ответы об ошибках по категориям, размеры пулов и свободные экземпляры, текущие и запущенные сессии в реальном времени, сегменты, отброшенные детектором голоса, и аудио в реальном времени, сброшенное отставшей сессией. Метрики `stt_pool_*` без меток описывают модель по умолчанию и диаризатор; метрики `stt_model_pool_size` и `stt_model_pool_available` с метками `model` и `backend` показывают каждую загруженную модель. Для каждой модели распознавания есть также две гистограммы и счётчик: `stt_model_inference_seconds` (метки `model` и `backend`) - сколько каждый вызов модели распознавал своё аудио, `stt_model_wait_seconds` (метка `model`) - сколько каждый заём ждал свободный экземпляр, а `stt_model_wait_timeouts_total` (метка `model`) считает ожидания, которые истекли: 503 после `STT_QUEUE_TIMEOUT` или сессию в реальном времени либо задание, прождавшие слишком долго; проба глубокой проверки health не попадает ни в одну из них. Обе гистограммы используют корзины 0.05, 0.1, 0.15, 0.2, 0.25, 0.3, 0.4, 0.5, 0.75, 1, 2.5, 5, 10, 30, 60 и 120 секунд, мелкие до одной секунды, чтобы короткие фразы различались. Как и health, этот эндпоинт не требует токена, и `stt_www` его не проксирует: опрашивайте `STT_PORT` напрямую. И так же, как у health, при заданном `STT_TOKENS` ряды по моделям попадают только в опрос с действительным токеном, потому что называют модели; без токена две метрики пулов пусты, а гистограмм задержки и счётчика истёкших ожиданий нет вовсе. Под gunicorn каждый рабочий процесс считает сам за себя.

`POST /api/stt` принимает поле `file` в формате `multipart/form-data` либо сырое тело `audio/*`. Необязательный параметр `model` (в строке запроса или как поле формы) выбирает одну из загруженных моделей: её id, алиас (`large-v3-turbo`, `parakeet-tdt-0.6b-v3`), форму `backend:model` или просто имя бэкенда, которое означает модель по умолчанию, если она принадлежит этому бэкенду, а иначе первую модель этого бэкенда. Без `model` отвечает модель по умолчанию. Необязательный параметр `language` (в строке запроса или как поле формы) переопределяет язык сервера по умолчанию для конкретного запроса; значение `auto` включает автоопределение. При успехе возвращаются текст, затраченное время в секундах, модель, которая распознавала, и язык: код, который Whisper определил или использовал (для англоязычной модели всегда `en`), либо `null` для Parakeet, который его не сообщает.

```bash
curl -X POST 'localhost:5051/api/stt?model=turbo&language=en' -F file=@speech.mp3
```

```json
{ "text": "transcribed text", "elapsed": 1.23, "model": "turbo", "language": "en" }
```

Язык можно задать кодом (`ru`) или английским названием (`russian`); всё, чего модель не знает, отклоняется с `400`, а не падает посреди расшифровки. `GET /api/models` перечисляет, что знает каждая модель. Насколько строго проверяется `language`, зависит от модели и от того, назвал ли её запрос:

| Модель | Какой `language` принимает | Запрос без `model` | Запрос с `model` |
| --- | --- | --- | --- |
| многоязычный Whisper | код или английское название из её списка | `400 Unsupported language` вне списка | так же |
| англоязычный Whisper (`.en`) | `en` и `auto` | другой известный код распознаётся как английский | `400 Unsupported language` |
| Parakeet | никакой, язык определяется сам | любое значение принимается и игнорируется | код из её списка, иначе `400` |

Parakeet принимает только коды, а не английские названия, и неуверенно распознанную речь может молча пропустить: в записи на нескольких языках для языка меньшинства он может не вернуть ничего.

У файла Whisper, чьё имя не совпадает ни с одним известным чекпойнтом (например, дообученной модели в `/models/my-large-v3-finetune.pt`), список языков лишь угадан по имени, поэтому запрос без `model` передаёт ему любой известный код, как и раньше; запрос, который называет эту модель, по-прежнему проверяется по угаданному списку.

Ошибки `400` для этих двух параметров: `Invalid model` (такое имя не знает ни один бэкенд), `Model not loaded` (настоящая модель, которую этот сервер не загрузил), `Invalid language` (это вовсе не язык) и `Unsupported language` (настоящий язык, который выбранная модель не принимает). Все четыре возвращаются до декодирования аудио.

`GET /api/models` сообщает, что умеет этот сервер, чтобы клиенту не приходилось угадывать. У каждой загруженной модели своя строка, как и у каждого распознавателя без загруженных моделей (`selectable: false`) и у диаризатора. Каждая строка приносит свой список языков, потому что наборы действительно расходятся, и объединённый список был бы неверен для каждой модели по отдельности.

```bash
curl -H 'Authorization: Bearer <token>' localhost:5051/api/models
```

```json
{
  "default": "whisper",
  "default_model": "turbo",
  "models": [
    { "id": "turbo", "backend": "whisper", "model": "turbo", "aliases": ["large-v3-turbo"], "status": "loaded",
      "selectable": true, "default": true, "pool_size": 2, "available": 2,
      "multilingual": true, "accepts_language": true, "languages_source": "derived",
      "languages": ["en", "zh", "de", "..."], "default_language": "en" },
    { "id": "small.en", "backend": "whisper", "model": "small.en", "aliases": [], "status": "loaded",
      "selectable": true, "default": false, "pool_size": 1, "available": 1,
      "multilingual": false, "accepts_language": true, "languages": ["en"], "default_language": "en" },
    { "id": "nvidia/Nemotron-3-Diarization", "backend": "diarize", "model": "nvidia/Nemotron-3-Diarization",
      "status": "installed", "selectable": false, "default": false, "pool_size": 1, "available": 0,
      "accepts_language": false, "languages": null, "max_speakers": 8 }
  ]
}
```

`id` это то, что запрос передаёт в `model`, и ровно у одной строки `default: true`: её id равен `default_model`, а её бэкенд это `default` верхнего уровня. `pool_size` и `available` описывают пул этой модели. `status` равен `loaded`, когда экземпляры загружены в её пул, свободны они или заняты, `installed`, когда веса лежат на диске, но ничего ещё не загружено, и `absent` в остальных случаях. Бэкенд, который настроен, но не установлен, отвечает `absent` и ничего больше; причина уходит в лог. `accepts_language` говорит, значит ли `?language=` вообще что-нибудь для этого бэкенда. Диаризатор сообщает `null` вместо пустого списка языков, потому что он не производит текст ни на одном языке.

CLI-клиент читает тот же эндпоинт:

```bash
python3 stt_client.py --list
```

`POST /api/diarize` отвечает на вопрос **кто и когда говорил**, и только на него: он возвращает временные интервалы с номером говорящего, но никогда не текст. Эндпоинт выключен, пока не задана переменная `DIARIZE_ENABLED` в образе, собранном с `DIARIZE=true`; иначе он отвечает `503`.

```bash
curl -X POST localhost:5051/api/diarize -F file=@meeting.wav
```

```json
{ "segments": [ { "speaker": 0, "start": 0.51, "end": 12.62 },
                { "speaker": 1, "start": 12.20, "end": 19.04 } ], "speakers": 2, "elapsed": 1.23 }
```

Два замечания об этих числах. Интервалы могут пересекаться, потому что канал каждого говорящего оценивается отдельно, поэтому двое говорящих одновременно дают два интервала, покрывающих одни и те же секунды. И метки это позиции внутри одной этой записи, упорядоченные по тому, кто заговорил первым: это не идентичности, и в следующем запросе тот же человек получит другой номер. Чтобы назвать говорящего по имени, нужен этап регистрации голоса, которого в этом сервисе нет. Различается не более восьми говорящих.

Доступны два бэкенда транскрипции. **Whisper** используется по умолчанию и принимает `language`. **Parakeet** (`nvidia/parakeet-tdt-0.6b-v3`) покрывает 25 европейских языков, определяет язык сам и поэтому не принимает аргумент `language` вовсе, о чём `GET /api/models` сообщает как `accepts_language: false`. Ему нужен образ, собранный с `PARAKEET=true`. Выберите его для всего сервера через `STT_BACKEND=parakeet` или загрузите рядом с Whisper через `STT_MODELS` и выбирайте в каждом запросе через `model`. Запрос выбирает только среди моделей, загруженных при старте, и каждая загруженная модель держит свои веса в каждом рабочем процессе, поэтому память равна числу воркеров, умноженному на сумму пулов.

Ни один из бэкендов не учитывает перекрывающуюся речь. Модель NVIDIA, учитывающая перекрытие, поставляется только как чекпойнт NeMo, а NeMo требует другую версию PyTorch, чем CUDA-сборка этого проекта, поэтому здесь она неустановима.

`POST /api/transcript` отвечает на вопрос **кто что сказал**: он прогоняет по одному и тому же аудио диаризацию и транскрипцию и соединяет их по времени. Ему нужна включённая диаризация, иначе он отвечает `503`. Он принимает те же `model` и `language`, что и `/api/stt`, и называет в `model` модель, которая распознавала.

```bash
curl -X POST localhost:5051/api/transcript -F file=@meeting.wav
```

```json
{
  "segments": [ { "speaker": 0, "start": 0.5, "end": 4.2, "text": "so where are we", "overlap": false },
                { "speaker": 1, "start": 4.0, "end": 9.8, "text": "green since this morning", "overlap": true } ],
  "turns": [ { "speaker": 0, "start": 0.51, "end": 4.24 }, { "speaker": 1, "start": 4.0, "end": 9.81 } ],
  "speakers": 2,
  "text": "so where are we green since this morning",
  "elapsed": 3.41,
  "model": "turbo"
}
```

`turns` это сырой вывод диаризатора, а `segments` результат соединения; они держатся порознь, чтобы клиент, не доверяющий привязке, всё равно видел, что сказал диаризатор. `text` это обычная транскрипция, совпадающая с тем, что `/api/stt` возвращает для того же файла. Фраза, которую не покрывает ни один интервал, сохраняет `"speaker": null`, а не отдаётся ближайшему.

`overlap` помечает фразу, во время которой говорил кто-то ещё. NVIDIA прямо указывает, что связка обычной модели на одного говорящего с диаризацией не равнозначна модели, построенной для перекрывающейся речи: извлечённый интервал времени всё равно содержит все голоса, которые его перекрывают, поэтому такие фразы могут смешиваться или брать слова не того говорящего. Считайте сегмент с пометкой `overlap` местом, где транскрипция заслуживает наименьшего доверия.

**Длинные записи идут через задание.** `POST /api/jobs` принимает тело в тех же формах, что и `/api/stt`, размером до `JOB_MAX_CONTENT_LENGTH_MB` (1 ГБ), а также `mode`: `text` (по умолчанию), `speakers` (результат `/api/transcript`) или `turns` (результат `/api/diarize`). Он сразу отвечает `202` с идентификатором задания и заголовком `Location`, который нужно опрашивать:

```bash
curl -F file=@meeting.mp3 'localhost:5051/api/jobs?mode=speakers&language=ru'
curl localhost:5051/api/jobs/1f0c3a9e7d2b4c85
```

```json
{ "id": "1f0c3a9e7d2b4c85", "status": "done", "mode": "speakers", "model": "turbo", "position": null, "seconds": 1801.6,
  "result": { "segments": ["..."], "turns": ["..."], "speakers": 4, "text": "...", "seconds": 1801.6, "model": "turbo" } }
```

`status` проходит `queued` (со своей `position`), `running`, затем `done` с `result` или `failed` с категорией `error`. `GET /api/jobs` перечисляет задания, а `DELETE /api/jobs/<id>` удаляет задание, которое сейчас не выполняется. Задание обрабатывает файл кусками примерно по минуте, нарезанными по паузам, и между ними отдаёт модель обратно, поэтому короткие запросы продолжают получать ответы, пока оно идёт: 30-минутная запись заняла 107 с на GPU, где развёрнут сервис, а запросы с телефонными звонками, отправленные в это время, заняли не больше 10 с. Диаризация проходит по всему файлу в потоковом режиме модели, поэтому говорящий сохраняет один номер от первой минуты до последней. Задания хранятся файлами в `JOBS_DIR`, поэтому переживают перезапуск, а завершённые удаляются через `JOB_RETENTION_HOURS`. Задание `text` или `speakers` принимает `model` и `language`, как `/api/stt`, и остаётся на этой модели: её называют и задание, и его результат, а задание, чью модель выгрузил перезапуск, завершается с `Model not loaded`. Задание `turns`, как и `/api/diarize`, не принимает `model`.

`/api/stream` это WebSocket для **транскрипции в реальном времени**: аудио поступает по мере записи, а каждая фраза возвращается примерно через секунду после того, как говорящий делает паузу. Управление передаётся текстовыми JSON-сообщениями, аудио передаётся бинарными сообщениями:

1. Клиент отправляет `{"type": "start", "model": "turbo", "language": "ru", "diarize": true, "token": "<token>"}`. Все поля, кроме `type`, необязательны. `model` выбирает одну из загруженных моделей так же, как `model` у `/api/stt`, и язык проверяется по этой модели; без него работает модель по умолчанию, а язык, как и раньше, проверяется лишь на то, что это вообще язык, поэтому код, которого модель по умолчанию не знает, приводит к ошибке при распознавании фразы. Через `token` аутентифицируется браузер, поскольку он не может задавать заголовки у WebSocket; другие клиенты могут вместо этого отправить `Authorization: Bearer <token>` при рукопожатии.
2. Сервер отвечает `{"type": "ready", "sample_rate": 16000, "backend": "whisper", "model": "turbo", "language": "ru", "diarize": true, "source": "client"}`.
3. Клиент отправляет сырой PCM - знаковый 16-битный little-endian, моно, 16 кГц - бинарными сообщениями любого размера в темпе записи, а по завершении `{"type": "stop"}`. Файл, отправленный быстрее реального времени, по замыслу отстаёт и теряет фразы (см. `skipped` ниже); файлу место в задании.
4. Сервер отправляет `segment` на каждую фразу, `progress` примерно раз в секунду, `skipped` с числом секунд отброшенного аудио, если сессия когда-либо отстанет больше чем на две минуты, и `done` перед закрытием:

```json
{ "type": "segment", "id": 3, "start": 6.88, "end": 8.2, "text": "This is the second speaker.", "speaker": 1, "overlap": false }
{ "type": "progress", "seconds": 12.3 }
{ "type": "done", "segments": 10, "seconds": 21.87, "elapsed": 22.08 }
```

Аудио может приходить и из другого места. С `"source": "url", "url": "https://..."` в стартовом сообщении клиент вообще не отправляет аудио: сервер читает поток по этому адресу через ffmpeg, пока тот не закончится или клиент не отправит `stop`. Работают интернет-радио, HLS, RTMP, RTSP и SRT; схема должна быть `http`, `https`, `rtmp`, `rtmps`, `rtsp` или `srt`. То, что живой источник уже накопил, забирается сразу, а остальное идёт в собственном темпе источника, так что удалённый файл приходит так же, как пришла бы трансляция.

Поскольку так сервер обращается по адресу, выбранному клиентом, эта возможность ограничена. ffmpeg может использовать только сетевые протоколы, поэтому ни URL, ни плейлист не заставят его прочитать локальный файл, и ничто не может заставить его слушать входящие соединения: режимы SRT `listener` и `rendezvous` и любой параметр `listen` отклоняются. Адрес, который является или разрешается в адрес самого сервера (loopback), link-local-адрес, например облачного сервиса метаданных `169.254.169.254`, или `0.0.0.0`, отклоняется как `Invalid stream URL`; проверка выполняется при запуске сессии, а ffmpeg по-прежнему следует перенаправлениям и плейлистам. Страница с другого сайта не может запустить такой источник (`Forbidden`): браузеры не применяют CORS к WebSocket, поэтому сокет проверяет, что источник (origin) страницы совпадает с этим хостом или указан в `CORS_ORIGINS`. В каждом процессе сервера одновременно работает не больше четырёх URL-источников (сверх этого `Service Unavailable`), так что gunicorn с несколькими воркерами допускает столько на каждый воркер, а в лог каждый адрес попадает без учётных данных и строки запроса. Хосты в собственной сети сервера по-прежнему достижимы: для камеры в этом и смысл, и это причина задавать `STT_TOKENS` на сервере, до которого могут дотянуться другие.

Ошибка это одно сообщение `{"type": "error", "error": "<category>", "request_id": "..."}`, за которым следует закрытие; категории те же, что у HTTP-ошибок, плюс `Invalid start message`, `Invalid audio frame`, `Invalid stream URL`, `Stream source failed` и `Forbidden`.

Фраза заканчивается на паузе в 0,6 с, там, где диаризатор слышит, что один говорящий передаёт слово другому (с `diarize`, поскольку люди, отвечающие друг другу, часто оставляют меньше 0,6 с), или, если она длится дольше 15 с, в самом тихом её месте, и транскрибируется отдельно моделью, взятой из того же пула, что и для загрузок, поэтому при занятом пуле фразы в реальном времени задерживаются, а не завершаются ошибкой. С `diarize` диаризатор работает в потоковом режиме и переносит кеш говорящих от фрагмента к фрагменту, поэтому говорящий сохраняет один и тот же номер на всю сессию. Сокет существует, когда сервер запущен под uvicorn: это `python3 stt_server.py`, вариант по умолчанию в Docker, или gunicorn с `GUNICORN_WORKER_CLASS=uvicorn_worker.UvicornWorker`, обслуживающий `stt_server:asgi_app`. Под отладочным сервером Flask и под рабочими процессами gunicorn типа sync, используемыми по умолчанию, его нет: они не поддерживают WebSocket.

**Возвращается только произнесённый текст.** Там, где речи нет, будь то тон, музыка, шум, гудки дозвона или даже цифровая тишина, Whisper отвечает титрами субтитрованных видео, на которых он учился ("Продолжение следует...", "Субтитры создавал DimaTorzok", "Thank you for watching."), и делает это с полной уверенностью: на тестовом корпусе его собственный `no_speech_prob` был 0,00 даже на тишине. Поэтому каждый эндпоинт прогоняет по аудио детектор голоса, Silero VAD, и отбрасывает транскрибированный сегмент, который в основном лежит вне обнаруженной речи, а также любой сегмент, целиком состоящий из строки титров. На корпусе из девяти записей без речи это убрало все такие строки и сохранило каждую фразу записей с речью. Запись, в которой ничего не сказано, теперь даёт пустой текст. В потоке в реальном времени фраза без обнаруженной речи даже не отправляется в модель. Детектор работает на CPU и добавляет примерно секунду на каждые три минуты аудио. `SPEECH_GATE=false` возвращает прежнее поведение.

Размер загрузки ограничен значением `MAX_CONTENT_LENGTH_MB` (10 МБ для сервера, запущенного напрямую, 100 МБ в сборке Docker); большее тело возвращает `413`.

Ошибки единообразны: `error` несёт обобщённую категорию, а `request_id` связывает ответ с записью в логе сервера, где зафиксировано полное исключение.

```json
{ "error": "Invalid audio data", "request_id": "a1b2c3d4e5f6" }
```

Если задана переменная `STT_TOKENS`, каждый запрос, кроме `GET /api/health`, должен содержать `Authorization: Bearer <token>`; сам `GET /api/health` остаётся открытым, чтобы продолжали работать проверки состояния.

### API, совместимый с OpenAI

`POST /v1/audio/transcriptions` и `GET /v1/models` повторяют аудио-API OpenAI, поэтому любой OpenAI SDK работает, как только его `base_url` указывает на `http://<host>:<port>/v1`, а ключ API - один из `STT_TOKENS` (при выключенной авторизации - любая строка).

```bash
curl localhost:5051/v1/audio/transcriptions \
  -H 'Authorization: Bearer <token>' \
  -F file=@phrase.wav -F model=turbo -F language=en -F response_format=verbose_json
```

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:5051/v1", api_key="<token>")
print(client.audio.transcriptions.create(model="turbo", file=open("phrase.wav", "rb")).text)
```

Запрос - это `multipart/form-data` с `file`, и он проходит ровно тот же путь, что и `/api/stt`: тот же токен, тот же лимит размера, то же преобразование, тот же фильтр речи и то же ожидание свободного экземпляра (`STT_QUEUE_TIMEOUT`). WAV 16 кГц, моно, 16-битный PCM передаётся без декодирования, всё остальное, как и на `/api/stt`, декодируется через pydub и преобразуется в 16 кГц моно.

- `model` - один из идентификаторов, которые перечисляет `GET /v1/models` (те же, что в `/api/models`), псевдоним или имя бэкенда, ровно как в `/api/stt`; без него или с пустым значением работает модель по умолчанию. Собственные имена OpenAI вроде `whisper-1` отклоняются как `Invalid model`.
- `language` проверяется по выбранной модели, как в `/api/stt`; Parakeet принимает его и игнорирует.
- `prompt` становится начальной подсказкой (initial prompt) Whisper. openai-whisper оставляет только последние 223 токена и использует её для первых 30 с аудио. Parakeet подсказок не принимает и игнорирует её. Подсказка со специальным токеном Whisper, например `<|endoftext|>`, отклоняется с 400 при любой модели. Подсказка никогда не пишется в лог.
- `temperature` может только отсутствовать или быть `0`: декодирование детерминированное, при температуре 0.
- `response_format` - `json` (по умолчанию, `{"text": ...}`), `text` (тело простым текстом) или `verbose_json`; `srt` и `vtt` отклоняются. `timestamp_granularities[]` может запрашивать только `segment`.

`verbose_json` содержит `task`, `language` (полное название языка строчными буквами, которое сообщает Whisper, например `english`, или `null` для Parakeet, который язык не сообщает), `duration` в секундах, `text` и `segments`. Сегменты Whisper - его собственные, с `id`, `seek`, `start`, `end`, `text`, `tokens`, `temperature`, `avg_logprob`, `compression_ratio` и `no_speech_prob`. Parakeet отдаёт один сегмент с пустым `tokens` и полями уверенности `null`, потому что он их не выдаёт.

Ошибки на любом пути `/v1`, включая `401`, `404`, `405`, `413` и `500`, имеют форму OpenAI, с той же категорией в `message`; каждый ответ `/v1` также несёт идентификатор запроса в заголовке `X-Request-Id`. Ошибки `/api/*` сохраняют свою форму.

```json
{ "error": { "message": "Invalid language", "type": "invalid_request_error", "param": "language",
             "code": "invalid_language", "request_id": "a1b2c3d4e5f6" } }
```

### CLI-клиент

`stt_client.py` это небольшой клиент для работы с сервером и его тестирования. Он читает адрес сервера и токен из `STT_URL` и `STT_TOKEN`.

```bash
python3 stt_client.py speech.mp3
python3 stt_client.py file1.wav file2.mp3 file3.ogg
python3 stt_client.py --model small.en --language en speech.mp3
python3 stt_client.py --list
```

`--model` и `--language` (также в виде `--model=ИМЯ`) отправляются, только если заданы, иначе действует значение сервера по умолчанию; каждая строка результата показывает модель и язык, которые использовал сервер. `--list` выводит модель по умолчанию и по строке на каждую модель: статус, можно ли выбрать её в запросе, пул и языки.

`--stream` проигрывает один файл в `/api/stream` со скоростью речи и печатает каждую фразу по мере её возвращения, а `--speakers` добавляет привязку к говорящим:

```bash
python3 stt_client.py --stream meeting.wav --speakers --model turbo --language ru
```

### Переменные окружения

`.env` загружается и сервером, и клиентом через `python-dotenv`.

| Переменная              | По умолчанию            | Назначение                                          |
| ----------------------- | ----------------------- | --------------------------------------------------- |
| `STT_HOST`              | `0.0.0.0`               | адрес привязки сервера                              |
| `STT_PORT`              | `5051`                  | порт сервера                                        |
| `STT_POOL_SIZE`         | `8`                     | экземпляров на модель; значение по умолчанию для записи `STT_MODELS` без `@pool` |

### Разработка

Должны присутствовать системные пакеты `ffmpeg` и `libsndfile1`. Установите рантайм- и dev-зависимости:

```bash
pip install -e ".[dev]"
pre-commit install
```

Makefile оборачивает типовые задачи:

```bash
make run            # foreground: python3 stt_server.py
make start          # background: PID -> .stt_server.pid, logs -> logs/stt_server.log
make stop           # stop the background server
make gunicorn       # run via gunicorn
make test           # pytest
make lint           # pre-commit (black + ruff)
make typecheck      # mypy
```

Набор тестов подменяет бэкенд Whisper заглушкой, поэтому он покрывает HTTP-слой (request_id, категории ошибок, семантику пула моделей) и выполняется за секунды без скачивания модели и без GPU.
